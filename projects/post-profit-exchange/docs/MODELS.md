# Inspectable demand forecasting and consumer simulation

The reusable [simple exponential smoothing tool](../../../tools/exponential-smoothing/README.md) owns the
EWMA mathematical core. Its pure C++17 target is `ph::exponential_smoothing`, with public
header `ph/exponential_smoothing/ewma.hpp`; it has no exchange or JSON dependency.
`simulation/models.hpp` and `models.cpp` retain the exchange adapters: strict
configuration and result JSON, stockout eligibility, declared price-response
normalization and the seeded consumer model. They contain no store ledger,
optimizer, file access, clock or network operation. Native and WebAssembly builds
use the same forecasting and application sources.

## Data provenance and cold start

No observed customer or sales dataset is supplied. The central
[exchange.cfg](../configs/exchange.cfg) starts from
[empty-history.json](../records/empty-history.json), whose observations are empty.
Before the first eligible sale, the bread and beans reference-price levels are
the configured `base_demand` assumptions of 20 and 14 units. The initial error
scale and continuing floor are the assumed 3 units, not a measured standard
deviation. Changing those settings changes the research assumptions.

The optional [sample-history.json](../records/sample-history.json) contains 14
explicitly synthetic rows, seven per SKU. It is only an opt-in import example and
test fixture. During a simulation, the seeded consumer generator produces sales;
eligible past sales update the level and squared error with configured
`alpha_bps=2500` (weight 0.25). The parameters themselves are not fitted. With real
records explicitly supplied, the same update uses those records. A
real imported history initializes the forecast; subsequent sales in this runner
are still generated by the simulation, not collected from live transactions. A
`min_history=7` value controls a warmup flag only; seven points do not establish
adequate data, forecast accuracy or calibrated uncertainty.

The consumer generator and forecast normalization share the declared
price-response priors. Agreement against this simulator therefore checks behavior
under those assumptions, not empirical demand accuracy or a learned causal effect
of changing prices. Synthetic records, prior assumptions and observed operating
records must remain distinguishable in any later dataset or evaluation.

## Interfaces and configuration

The namespace is `ph::exchange::models`. `consumer_config(Json)` and
`forecast_config(Json)` require every field below, reject unknown fields and
validate types and bounds. The typed interfaces validate their inputs as well.
`to_json` overloads expose configuration and results.

| Consumer field | Meaning and bounds |
| --- | --- |
| `potential_visitors` | Independent visitor opportunities per day, 0–10,000; default 100. |
| `visit_probability_bps` | Arrival probability, 0–10,000 basis points; default 8,000. |
| `budget_min`, `budget_max` | Inclusive integer cash-budget range, ordered in 0–100,000,000 minor units; defaults 500 and 2,000. |
| `need_probability_bps` | Per-visitor, per-product need probability, 0–10,000; default 5,000. |
| `max_units_per_product` | Desired quantity is uniform on 1 through this value after choosing to buy, 1–10; default 2. |
| `choice_scale_bps` | Positive price-utility scale, 1–30,000; default 4,000. Greater scale weakens price response for a fixed slope. |

Each `ProductPrior` contains a unique `sku` of 1–64 bytes without controls,
`reference_price` of 1–1,000,000 minor units, `base_demand` of 0–10,000 units and
`elasticity_bps` of 0–30,000. The last name is retained for configuration
compatibility; it is a declared utility slope, not an estimated economic elasticity.
The consumer module accepts 1–12 products and matching price/stock vectors.

| Forecast field | Meaning and bounds |
| --- | --- |
| `model` | Exactly `ewma`. |
| `alpha_bps` | Level and squared-error smoothing weight, 1–10,000; default 2,500. |
| `sigma_multiplier_bps` | Stress multiplier `z`, 0–100,000; default 30,000 means 3×. |
| `min_history` | Eligible observations required for the warmed-up flag, 1–3,650; default 7. Learning begins before that threshold. |
| `prior_sigma_units` | Finite initial RMS forecast error and continuing floor, 0–1,000,000 reference-price units; default 3. Fractions are allowed. |
| `reserve_horizon_days` | Application planning horizon, 1–365; default 7. The module does not allocate reserves. |

`EwmaForecaster(config, prior_level)` initializes one SKU with a finite level in
0–1,000,000 reference-price units. `predict(response, horizon)` is a pure read;
`observe(day, sales, stock, response, trading)` scores the pre-update forecast and
then learns. `diagnostics()` reports state and walk-forward errors. Callers choose
the explicit horizon passed to `predict`; the default is one day.

## Consumer generation

`consumers_day(config, priors, prices, stock, seed, day, demand_factor_bps)` runs
these gates for each potential visitor:

1. Arrive with the configured visit probability multiplied by the day's demand
   shock. The resulting basis-point probability is rounded and capped at one.
2. Draw an inclusive integer budget. For each SKU in configured order, draw need.
3. Conditional on need, choose purchase versus the outside no-purchase option
   using binary-logit probability at the posted price.
4. Draw desired units, limit them by the remaining budget, then limit fulfillment
   by remaining stock. Pay only for fulfilled units and continue to the next SKU.

Let `O` be expected units with arrival and need gates but without choice, budget
or stock limits. It equals potential visitors × visit probability × need
probability × `(max_units_per_product + 1) / 2`. The declared base demand
calibrates a reference choice probability `p0 = base_demand / O`, rounded to
millionths. Positive values are constrained to `[0.000001, 0.999999]`; zero base
demand or zero opportunities yields zero choice probability. A prior exceeding
opportunities is reported as unattainable by `consumer_prior`, not represented
as an empirical estimate.

With `k = elasticity_bps / choice_scale_bps`, the utility relation is:

```text
logit(p(price)) = logit(p0) - k * (price / reference_price - 1)
```

The inspectable implied valuation solves that utility at zero; it is a synthetic
parameter, not an individual's willingness to pay. Binary logit supplies an
explicit purchase/no-purchase response. This implementation does not fit a
multinomial substitution model. The underlying choice-model family is described
in Kenneth Train's [Discrete Choice Methods with Simulation, chapter 3](https://eml.berkeley.edu/books/choice2.html).

Choice probabilities are calculated from odds using integer arithmetic, a
bounded Taylor/squaring approximation to `exp(-abs(utility_change))`, and
millionth quantization. Absolute utility change is capped at 20 before that
approximation. Reference calibration, choice thresholds, budget draws and
payments do not depend on native/WASM transcendental-library rounding. A
floating logarithm is used only to report implied valuation, never to decide a
purchase. Tests compare the approximation with the binary-logit formula.

Random draws use fixed-width unsigned hashes keyed by seed, signed day, customer
index, SKU and event type. They do not consume a shared advancing stream. Thus
changed prices, stockouts or a skipped need do not shift subsequent draws. Both
policies see matching arrival, budget, need, choice and desired-quantity draws;
their actual purchases may differ. These are synthetic pseudorandom numbers,
not privacy-preserving identifiers or cryptographic randomness. Mapping 32-bit
draws to arbitrary integer ranges has finite-resolution discretization.

`ConsumerDay` reports effective arrival probability, visitors, no-visits,
visitors with no fulfilled purchase, opening/remaining budget and spending.
Per SKU it reports choice probability, need/no-purchase counts, desired units,
budget-rejected units, affordable requested units, sold units, stock-lost units
and revenue. Per-SKU `no_purchase_customers` counts conditional logit rejections
after a need; day-level `no_purchase` counts visitors who bought nothing after
all choice, budget and stock gates. Exact identities are:

```text
visitors + no_visit = potential_visitors
opening_budget = remaining_budget + spending
desired_units = budget_rejected_units + requested_units
requested_units = sales_units + stock_lost_units
spending = sum(price * sales_units)
```

SKU order is an explicit limitation: earlier products consume budget first.
Unfulfilled demand does not spend budget, so stockouts can free funds for later
SKUs. No household persists between days; travel, competitors, substitution,
joint basket utility and income dynamics are absent. Financial access is visible
through budget rejection, but the synthetic budget distribution is not evidence
about real customers.

## Forecasting from prior observations only

Simple exponential smoothing maintains a recent weighted level and is a baseline
for series without modeled trend or seasonality. Here its parameters are supplied,
not fitted to historical error. See [Forecasting: Principles and Practice, simple exponential smoothing](https://otexts.com/fpp3/ses.html).

For the chosen price, `price_response_factor` is choice probability divided by
the reference probability. It normalizes observed sales before learning and
converts the reference-price forecast back to candidate-price units. To keep
normalization defined, a nonzero prior uses a one-millionth probability floor
even when a quantized candidate choice probability becomes zero. A zero-opportunity
or zero-base prior instead uses neutral response 1. These declared response
assumptions are exposed; price effects are not learned from sales.

For eligible observation `y_t`, response `r_t` and prior level `L_(t-1)`:

```text
prediction_t = r_t * L_(t-1)
normalized_error_t = y_t / r_t - L_(t-1)
L_t = (1-alpha) * L_(t-1) + alpha * (y_t / r_t)
V_t = (1-alpha) * V_(t-1) + alpha * normalized_error_t^2
sigma_normalized = max(prior_sigma_units, sqrt(V_t))
```

This sigma is an exponentially weighted RMS one-step forecast error, not an
unbiased sample standard deviation centered on a separately estimated residual
mean. It includes persistent forecast bias. All predictions are recorded before
their observation changes level or error state. Negative days permit explicit
pre-run history; days must then strictly increase. The model receives neither
future consumer draws nor future demand shocks.

Sales equal to available stock are conservatively treated as censored, including
zero stock. Closed periods are also excluded. These observations update neither
level nor residual statistics; uncensored zero sales do update both. The module
never trains on simulator-known latent demand. External history explicitly
declared uncensored may use `sales + 1` as an internal stock sentinel. Accordingly,
sales are capped at 1,000,000 and that sentinel at 1,000,001; it does not represent
actual extra inventory. Callers must supply honest censoring metadata.

Skipping stock-censored observations avoids equating a stockout with weak demand,
but creates selection bias and may leave a poorly stocked SKU at its prior for
many days. This is not a censored-demand estimator. SKU budgets and other prices
also affect realized sales, while normalization uses only the SKU's own declared
choice response. Such mismatch can remain in errors.

Walk-forward diagnostics report MAE, RMSE and configured-band coverage in actual
units at each observation's price. Both all eligible observations and only those
predicted after warmup are reported; no observations yields `null`, not zero
error. Coverage excludes censored/closed periods and must be interpreted within
that selected sample. This ordering follows [time-series cross-validation](https://otexts.com/fpp3/tscv.html).
Error bias, dependence and changing variance still need investigation; small
reported error alone does not validate a model. See [residual diagnostics](https://otexts.com/fpp3/diagnostics.html).

## Uncertainty and reserve use

One-day output is `mean = response * level`, `sigma = response * sigma_normalized`
and `[max(0, mean-z*sigma), mean+z*sigma]`. These are configured stress bands, not
certified coverage probabilities. In particular, choosing `z=3` makes no 99.7%
claim without distributional and calibration evidence.

For a constant response across `H` future days, the module reports cumulative
mean `H * mean`. Under the additive-innovation SES assumptions of uncorrelated,
equal-variance innovations, cumulative forecast-error sigma is:

```text
sigma_H = sigma * sqrt(sum(j=0..H-1, (1 + alpha*j)^2))
```

Those coefficients account for a future innovation changing later levels. This
conditional formula omits parameter uncertainty, autocorrelated shocks,
censoring bias, saturation and structural change. The lower band is truncated
at zero; this does not make the errors Gaussian. `horizon_mean` and
`horizon_sigma` refer to cumulative demand, not just the final day's demand.

The exchange application separately constructs a reserve stress target from
current-price expected contribution and per-SKU one-step sigma. For fixed daily
obligations `F`, current margins `m_i`, means `mu_i`, and horizon `H`, its rule is:

```text
target = max(configured_reserve_target,
    ceil(H * max(0, F - sum(m_i * mu_i))
         + z * H * sum(abs(m_i) * sigma_i)))
```

This deliberately uses a common adverse error across products and days rather
than assuming diversification. The absolute-margin sum is a conservative
aggregation of the supplied marginal error scales under that stress assumption;
it is not an absolute worst-case bound, calibrated insurance price or guarantee
of sufficient reserves. It differs from the module's uncorrelated-innovation
cumulative sigma. Changing the learned level/error can change the target; reserve
cash earmarking and newly scheduled funding remain separate application ledgers.
For the reserve calculation, each mean is capped by both physical consumer-unit
capacity and `max(current_stock,target_stock)`; each sigma is capped by physical
capacity. The stock target is a replenishment heuristic, not proof that cash can
finance all those units. Raw forecast outputs remain separately inspectable.

Forecaster outputs are finite doubles, not clipped to inventory. Extreme
normalization can produce large values; observations beyond 10^12 normalized
units are rejected. Callers must explicitly bound physical demand before integer
conversion and expose any cap. The application additionally rejects reserve
estimates beyond its exact-arithmetic bound instead of silently overflowing.

## Validation boundary

The exponential-smoothing tool has its own `exponential_smoothing_ewma` CTest entry covering typed
inputs, update equations, skipped observations, warmup and horizon uncertainty
without linking the exchange, JSON library or optimizer.

`models_test.cpp` checks strict parameters, prior-only update order, imported
history, warmup, censored/closed learning exclusion, sigma floor and cumulative
uncertainty; plus consumer replay, paired draws, monotone choice response before
budget competition, exact budget/stock accounting, no-visit/no-need/no-budget
cases and the 12-product bound. These checks establish implementation properties,
not real-world demand accuracy or browser interaction coverage.

## Future TFT integration

The separate [Temporal Fusion Transformer tool](../../../tools/temporal-fusion-transformer/README.md)
is not called or trained by exchange. Its architecture supports static inputs,
historical observations, known-future covariates and multiple forecast horizons;
these capabilities make it a candidate for later evaluation, not evidence that it
will improve this application. See the [TFT paper](https://arxiv.org/abs/1912.09363)
and the local [replication gate](../../../docs/tft-replication.md).

Short histories favor a small baseline that can be inspected and compared. There
is no universal observation-count threshold that establishes useful forecasting:
noise, model complexity and the evidence available for validation matter. This
choice follows [Forecasting: Principles and Practice on very short series](https://otexts.com/fpp3/long-short-ts.html).
A TFT can mechanically fit a small set of complete windows, but fitting does not
establish reliable prediction or tail calibration. Do not create artificial
operating observations to make a training set appear adequate, or treat many
overlapping windows as independent evidence. Future integration needs an explicit
data/feature contract, chronological evaluation against the baseline and adequate
separate evidence for uncertainty calibration. No TFT adapter or training run is
part of the current extraction.
